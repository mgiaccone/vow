# Contributing to vow

Issues and pull requests are welcome.

## Getting started

```
git clone https://github.com/mgiaccone/vow
cd vow
go test ./...
```

No setup beyond a Go 1.24+ toolchain. `vow` has zero third-party
dependencies, so there is nothing to install.

## Before opening a pull request

```
go vet ./...
gofmt -l .            # must print nothing
go test ./...
```

If you changed the generator, also confirm the committed output is current:

```
go generate ./...
git diff --exit-code
```

CI runs exactly these, so a green local run means a green build.

## Changing the generator

Generated output is checked into `example/` and `internal/testdata/`, so any
generator change shows up as a golden-file diff. The workflow:

1. `go test ./cmd/vow -update` to refresh the golden files.
2. **Read the diff by eye.** Don't accept it because the tests pass — the
   tests compare against whatever you just wrote. You are reviewing the
   generated Go, not the diff's size.
3. `go generate ./...` and confirm `example/` still builds and vets.
4. Run generation twice and confirm the second run produces no diff. Output
   must be byte-identical across runs, or the CI freshness check becomes a
   source of spurious failures.

## Layout

- `vow.go`, `sanitizers.go`, `rules.go`, `collect.go` — the runtime, at the
  module root so consumers write `vow.Spec[string]{...}` after one import.
- `cmd/vow/` — the generator. Never a runtime dependency; nothing in it may be
  imported by root-package code.
- `internal/testdata/` — golden fixtures. Go ignores directories named
  `testdata`, which is why fixtures can reference not-yet-generated code
  without breaking the build.
- `example/` — dogfoods the generator through the `tool` directive in
  `go.mod`, and holds the runnable godoc examples.
- `README.md` — the user-facing documentation. There is no `docs/`.

## Invariants

Each of these exists for a reason that a quick fix will route around if you
don't know it. Read the reason before working around the rule.

- **No underscores in user-facing names** — flags, tag keys and values,
  directives, sanitizer names. Hyphens only where unavoidable.
  `sanitize=trim|collapse` has to stay unambiguous with no separator.
- **Zero third-party dependencies, anywhere, including tests.** This is the
  whole pitch to anyone weighing a codegen tool; one `require` line undoes it.
- **No type-checking in the generator, and no `x/tools`.** `go/types` appears
  exactly once, as `types.ExprString` — a syntactic printer, not a checker.
  Don't "improve" it into real type-checking; see the next invariant.
- **The generator must work on a package that does not compile.** First
  adoption always begins with code calling `NewEmail` before `NewEmail`
  exists. Discovery uses `go/parser` and purely syntactic checks for exactly
  this reason.
- **No validation rules in struct tags.** Tags are backtick literals: no
  embedded quotes, and splitting on `,` corrupts any regex containing one.
  Rules stay ordinary, type-checked Go.
- **`Rule[T]` stays `func(T) error`, and a type resolves exactly one spec.**
  A rule that could see sibling fields would make the value object know about
  its container, and it would stop being reusable anywhere else. Validation
  that depends on another value is expressed by the spec being a *func* whose
  parameters reach the constructor — one spec, taking arguments — not by
  widening either of these.
- **No `UnmarshalJSON` on generated types.** A decode error carries no field
  identity, so it can't join a `Collector` result.
- **No validation in `Scan`.** Retiring an enum member or tightening a rule
  must never make historical rows unloadable.
- **One output file per package, not configurable.** Spec vars and enum consts
  resolve across the whole package, so the package is already the unit of
  input. Per-file output would require deleting files the generator believes
  it owns — which it must never do.
- **`vow` never deletes a file.** It writes exactly `-out` and touches nothing
  else. When a package's last tagged type is removed, it errors and names the
  stale file rather than clearing it.
- **Output must be byte-identical across runs.** Sorted declarations, sorted
  map iteration, and no `time.Now()`/`math/rand` in generation. This is what
  makes `go generate ./... && git diff --exit-code` a valid CI check.

## Conventions

- Every generation error carries a `token.Position`, names the type, and
  states the fix — see `errAt` in `cmd/vow/errors.go`.
- Rule messages are transport-neutral sentence fragments ("must be at most 254
  characters"), never full sentences or HTTP-flavored. Built-in rules return
  an unexported `ruleError` rather than `fmt.Errorf("...: %w", sentinel)`, so
  the sentinel's own text doesn't leak into the fragment; `errors.Is` still
  reaches it.
- Generated files start with `// Code generated by vow. DO NOT EDIT.`.
- Iterate in sorted order everywhere output reaches disk.

## Proposing new features

Open an issue first for anything that changes the public API, adds a struct
tag or directive option, or adds a dependency. The generated method set and
the built-in rule set are deliberately small; additions need a case, not just
an implementation.

Several things are deliberately out of scope — struct validation,
`UnmarshalJSON`, validation inside `Scan`, multi-field value objects, and
rules expressed in struct tags. The README's [Gotchas][g] and [What Go will
not let this library do][w] sections explain the reasoning for each.

[g]: README.md#gotchas
[w]: README.md#what-go-will-not-let-this-library-do

## Commit messages

Describe what changed and why. The "why" matters more — the diff already
shows the what.
